# Реліз KuubMill на прод

Прод (`127.0.0.1:8000`, встановлений `KuubMill.exe`) оновлюється **сам**, раз на добу перевіряючи GitHub Releases і встановлюючи новіший інсталятор. Твоя робота — зібрати й опублікувати цей інсталятор через тег. Хмара робить решту.

**Ланцюг:** журнал змін → bump версії → тести → commit → tag `vX.Y.Z` → push → CI збирає+smoke-тестить+публікує реліз → 8000 підхоплює.

## Кроки

1. **Написати запис у журнал змін** — у розділ `## [Незалежно від версії]` на
   початку `CHANGELOG.md`. Формат Keep a Changelog: підрозділи `### Додано` /
   `### Виправлено`. Мова — «що змінилось для оператора», не технічні деталі
   (дивись попередній запис як зразок). Крок НЕ пропускати: `bump_version.py`
   лише проштамповує цей розділ номером і датою, сам тексту не пише, і реліз
   з порожнім розділом виходить безмовним.

2. **Підняти версію** (штампує `__version__.py`, `.iss` і заголовок у
   `CHANGELOG.md`):
   ```
   python bump_version.py X.Y.Z
   ```
   Сам не редагуй версію руками — легко проґавити одне з місць і завалити CI.

   `release.yml: 0 замін` — це НОРМА, а не збій: workflow бере версію з тега
   (`github.ref_name`), зашитого рядка там більше немає. Докстрінг самого
   `bump_version.py` ще каже «в чотирьох місцях, workflow 6 разів» — застарів.

3. **Прогнати ТІ САМІ ворота, що й CI, і в тому ж порядку:**
   ```
   .venv/Scripts/python.exe -m ruff check .
   .venv/Scripts/python.exe -m pytest tests/test_version_sync.py -q
   .venv/Scripts/python.exe -m pytest -q
   ```
   **Лінтер ПЕРШИМ — так само, як у CI.** Він стоїть там окремим кроком і раніше
   за тести, тож зелені тести нічого не обіцяють: 0.13.11 упав саме на `ruff`
   (дві мертві змінні після рефакторингу) при 2584 зелених тестах, і тег довелось
   переставляти. `test_version_sync` падає, якщо `__version__` розійшовся з `.iss`.
   Не релізити з червоним будь-чим із трьох.

   Якщо в блоці був JS — ще `node --check` на змінені файли (див. CLAUDE.md §15).

4. **Закомітити бамп** (окремим комітом, із Co-Authored-By трейлером):
   ```
   git add app/__version__.py installer/KuubMill.iss CHANGELOG.md
   git commit -m "Release X.Y.Z: bump version + журнал змін"
   ```
   `CHANGELOG.md` тут ОБОВ'ЯЗКОВИЙ — його штампує `bump_version.py`, і без
   нього в комміті реліз їде з журналом попередньої версії. `release.yml` у
   цьому списку більше не потрібен: він не змінюється (див. крок 2).

5. **Тег + пуш = тригер релізу** (це незворотна вихідна дія — підтверди в користувача перед пушем):
   ```
   git tag -a vX.Y.Z -m "KuubMill X.Y.Z — <підсумок>"
   git push origin vX.Y.Z
   ```
   Пуш тега несе й коміти. CI (`.github/workflows/release.yml`) запускається на `tags: v*`.

6. **Дочекатись CI** (windows-latest, ~3 хв: onedir + Inno Setup + до 180с smoke health-check):
   ```
   gh run watch <run-id> --repo kuubek5/order-desk --exit-status
   ```
   Запусти у фоні (`run_in_background`), не блокуй. Репозиторій тут
   `order-desk` — прогін живе там, де код.

7. **Підтвердити реліз — у РЕЛІЗНОМУ репозиторії, не в тому, де код:**
   ```
   gh release view vX.Y.Z --repo kuubek5/order-desk-releases --json assets --jq '.assets[].name'
   ```
   Мають бути `KuubMill-Setup-X.Y.Z.exe` + `.sha256`.

   Два різні репозиторії, і їх легко переплутати: код і CI — у приватному
   `kuubek5/order-desk`, а сам реліз workflow свідомо публікує в публічний
   `kuubek5/order-desk-releases` (крок «Create GitHub Release», `repository:`
   + `RELEASES_REPO_TOKEN`). Туди ж дивиться авто-оновлення застосунку
   (`GITHUB_REPO` у коді). Запит до `order-desk` віддає «release not found»
   при цілком зеленому CI.

8. **Доставка на 8000:** автоматична, до доби. Прискорити — рестарт встановленого додатку (update-check спрацьовує через ~30с після старту). Рестарт прод-процесу — лише з дозволу користувача.

## Пастки

- Версія зашита в `__version__.py` і `.iss` — `bump_version.py` покриває обидва плюс заголовок журналу; руками не правити. Workflow версію більше не тримає (бере з тега), тож «Verify installer exists» через проґавлений sed уже не падає.
- **Журнал змін пишеться ДО бампу і комітиться РАЗОМ із ним.** Обидва кроки легко пропустити, бо CI на них не свариться: тести зелені, реліз виходить — просто мовчазний або з чужим текстом.
- Провал smoke-тесту в CI → реліз НЕ створюється (безпечно, 8000 лишається на старій версії). Читай хвіст логу CI + `startup-error.txt` із артефактів.
- Авто-оновлення має відому пастку (watchdog + frozen-app subprocess) — див. `[[project_orderdesk_autoupdate_trap]]` у пам'яті. Якщо 8000 не оновлюється — інсталятор можна запустити вручну з `%LOCALAPPDATA%\KuubMill\updates\`.
- Тег незворотний — перед пушем звірити версію й що всі потрібні коміти в HEAD.
- **Список релізів у `order-desk` завмер на v0.3.0 (17.08.26) — це НЕ втрачені
  зміни.** Той тег є предком поточної гілки, його код давно всередині свіжих
  версій; просто до кінця серпня релізи публікувались у самому репозиторії
  коду, а потім публікація переїхала в окремий публічний `order-desk-releases`
  (найраніший там — v0.6.12 від 02.09.26). Ассет того часу ще зветься
  `OrderDesk-Setup-…` — до перейменування в KuubMill. Побачивши «v0.3.0 Latest»,
  не лізь відновлювати нічого: дивись у релізний репозиторій.
