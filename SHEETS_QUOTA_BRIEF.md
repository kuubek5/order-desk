## Крок 0. Чи є проблема взагалі — виміряти на проді (цеховий ПК)

Лог проду: `%LOCALAPPDATA%\KuubMill\logs\kuubmill.log` (+ `.1`…`.5`, по 2 МБ).

Основний спосіб — `scripts/quota_report.ps1`: вставляється в Windows PowerShell на цеховому ПК цілим блоком,
кладе `kmill-quota-report.txt` на Робочий стіл і відкриває його в Блокноті. Лише ASCII (безпечно для PS 5.1),
лог читає з `FileShare.ReadWrite` (прод пише в нього одночасно). Перевірено 10.09.26 на штучному лозі під PS 5.1.
Звіт: запити/хв (середнє, макс, хвилин ≥45 і ≥60) по днях і годинах, пропуски гарячого тіку, Google-429
«Quota exceeded» і інші 429 (проксі?) по днях. Запускати після ~12:00, щоб у лозі був ранковий пік.

Дві команди нижче — те саме вручну, коротко:

```powershell
# скільки разів гарячий тік пропущено через квоту і скільки справжніх 429
Select-String -Path "$env:LOCALAPPDATA\KuubMill\logs\kuubmill.log*" -Encoding UTF8 -Pattern "Гарячий тік пропущено|Quota exceeded" | Group-Object { $_.Line -match "Quota exceeded" } | Select-Object Name, Count
```

```powershell
# запитів за хвилину: середнє і максимум (рядок пишеться раз на хвилину)
Select-String -Path "$env:LOCALAPPDATA\KuubMill\logs\kuubmill.log*" -Encoding UTF8 -Pattern "Sheets API: (\d+) запит" | ForEach-Object { [int]$_.Matches[0].Groups[1].Value } | Measure-Object -Average -Maximum
```

Висновок:
- максимум < 40 і пропусків нема → квота зараз не заважає, кроки нижче лише запас на майбутнє (Турбо, другий оператор);
- пропуски є або максимум ≥ 45 → робимо кроки 1–2.

## Прогалина у вимірах: тривалість тіку на проді

Свіжість «таблиця → CRM» = інтервал тіку + ТРИВАЛІСТЬ тіку (читання значень і заливок через проксі лаби:
за коментарями в коді ~3 с на `get_all_values`, до ~18 с на холодні метадані) + пропущені тіки.
Тривалість фонового тіку ніде не міряється: `/diag/perf` бачить лише HTTP-запити. Перед тим як міняти
інтервали, додати вимір (кільце в `/diag/perf` або рядок через `log_throttle`): тік → скільки секунд,
скільки запитів, які вкладки. Без цього «швидше» не має числа.

## Кроки (від меншого ризику)

1. **Заливки кількох вкладок одним запитом.** Повний/широкий синк читає заливки кожної вкладки окремо.
   Один `fetch_sheet_metadata` з кількома `ranges` → один `GetSpreadsheet`. Значення не чіпати.
2. **Не читати ту саму вкладку кілька разів за хвилину.** Сьогоднішню вкладку читають hot, wide і full.
   Спершу виміряти число дублів на dev (лічильник `_record_api_call` + мітка «яка вкладка, який тік»), потім
   дедуп «вкладку прочитано < N с тому → пропустити».
3. **Дослідити** Drive API `modifiedTime` як ворота «таблиця не змінилась → не читати». Перш ніж покладатись:
   виміряти на тестовій таблиці (§12) затримку оновлення після правки клітинки І після зміни заливки.
   Потребує увімкнення Drive API в проєкті й scope лише на метадані.
4. **НЕ в цьому блоці:** значення + заливки одним запитом. Зачіпає інваріант §14 «читання вкладки — ОДИН
   `get_all_values`», потребує доказу байт-у-байт на справжніх вкладках. Окремим блоком, якщо 1–2 не вистачить.

## Інваріанти, які не зламати

- `fetch_row_fills` на збої повертає **None, не `{}`** (порожній словник = «усі видані», ревʼю 07.09.26 CRITICAL-3).
  Пакетне читання мусить на збої давати None для КОЖНОЇ вкладки, а не частковий результат.
- Кожен виклик Google — через `call_with_retry`, інакше лічильник квоти й гальмо його не бачать.
- Запобіжники архівації (зникла вкладка, `_absent_streak`) дивляться лише на СВІЖИЙ лістинг повного синку — не на кеш.
- Назви вкладок — лише через `canonical_tab_title()`.
- Числа `GOOGLE_QUOTA_PER_MINUTE=60` / `GOOGLE_QUOTA_SOFT_LIMIT=45` не піднімати: Google відмовив.
