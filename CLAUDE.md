# KuubMill — контекст проекту

Постійний контекст. Claude Code читає на старті сесії. Журнал змін — `HISTORY.md` (не автозавантажується).

## 1. Що це і навіщо

Фрезерний центр дентальної лабораторії: ~10 верстатів imes-icore, коронки/абатменти/каркаси з цирконію, ПММА, титану. Два джерела робіт, зараз зводяться вручну в Google Таблицю. KuubMill — окремий сервіс (не модуль CNC Tracker): одна робоча черга з обох джерел, авто-синк з таблицею, закриває найболючіше — ранкову видачу.

## 2. Робочий процес (як є зараз)

**Джерело 1 — лабораторія.** Технік моделює, кладе файли на сервер, пише рядок у таблицю: наряд, колір/матеріал, к-сть одиниць, вид, дедлайн. Оператор копіює номер у Sum3D (CAM) для прорахунку.

**Джерело 2 — пошта (ukr.net), уся країна.** Файли листом, у тексті — матеріал, фрезерування/на фрезерування, колір. Зараз оператор вручну качає вкладення й дописує рядок (клієнт, колір, матеріал, к-сть).

**Взяття в роботу.** Оператор прораховує в Sum3D, вписує в таблицю ID проекту Sum3D.

**Синтеризація (пічка).** Тільки цирконій; ПММА/титан/віск готові після фрезерування (зазвичай чекають і видаються разом, термінові — раніше). Три пічки + допоміжна. Закладка ~17:00 (основна), ~22:00, до ~03:00. Відкриття наступного дня ~9:00 / обід / вечір. Роботи одного клієнта — в різних пічках → **часткова видача = норма**. Окремого статусу «у пічці» нема (свідомо).

**Видача (найболючіше).** Зранку основна маса, решта до обіду й пізніше. Оператор іде списком клієнтів згори вниз, шукає коронку в лотку, звіряє форму з STL-прев'ю (повноекранно). Знайшов → підписує пакетик → відмічає (зараз — знімає синю заливку рядка). Логіст забирає → кур'єр.

Три правила видачі (порушити = зламати роботу):
1. **Порядок списку фіксується на початку дня.** Жодного авто-пересортування під руками (полл не міняє порядок).
2. **Один клік на дію, без зайвих підтверджень.** Галочка «знайдено» на рядок — і все: вона знімає синю заливку рядка в таблиці, а саме заливка, не статус у базі, є сигналом видачі для всієї лабораторії. Кнопку «Видати N з M» прибрано 07.09.26 (нею не користувались); два кроки з 03.09.26 більше не діють. Жодна дія не вимагає другого підтвердження.
3. **Ніякого авто-зіставлення.** Спільного ключа рядок↔коронка нема, розрізняють оком. Система показує кандидатів і STL, рішення за оператором.

**Втрачена робота** (є в таблиці, фізично нема — випала при фрезеруванні або не виготовилась). Поза системою, не реалізовувати без прохання.

Таблицю дивляться логісти, адміністратори, техніки — пишуть зауваження. Портал синхронізується з нею в обидва боки, не замінює. Таблиця лишається на час тестування.

**Терміновість.** Дедлайни «Здати до» не враховуються. Реальний сигнал: лабораторія — «**на швидку**» в коментарі техніка (швидка програма спікання); клієнти — окремий лист адміністраторів.

## 3. Структура Google Таблиці

- Один файл, вкладка на день, назва = дата `22.07.26` (дд.мм.рр).
- Заголовки рядки 2-6, дані з рядка 7.
- Колонки:
  - № (порядковий)
  - Номер наряду (`24122`)
  - Кількість (одиниць)
  - Колір роботи (`пмма A2`, `моно А3.5`, `титан корея`, `500`, `800`). `500` = A1 опак, `800` = A2 опак (кольори виробника).
  - Вид роботи (`анатомія`, `анатомія гвинтова`, `абатмент`, `каркас міст 13-23`, `вкладка`)
  - Здати до — підколонки `14:00` / `16:00` / `09:00`, позначка `x` (не враховується, див. §2)
  - Номер роботи (`Order.job_code`) — **мережевий шлях/папка, куди технік поклав роботу** = ознака «технік здав». Формат непослідовний (`2026-07-21_00016-007` або дубль наряду `23203`). Заповнено ~третина рядків — норма. **Не плутати з Sum3D ID, не видаляти** — на ньому фільтр готовності.
  - Ім'я техніка
  - Коментар для CAM-оператора («на швидку» = терміново)
  - ID Sum3D (`Order.sum3d_id`) — оператор після взяття. Використовують лише хвіст — час `HH-MM-SS` (`12-01-45`). Головний ідентифікатор, заповнений майже скрізь.
  - Прорахував / Відфрезерував — позначки + час
  - Дата останнього фрезерування
  - Який раз фрезерується
  - БРАК: винен обладнання / технік / адміністратор / клієнт + к-сть одиниць переробки
  - Ручна підсвітка рядків (помаранчевий/зелений) — не формалізована.

## 4. Структура папки export (для ранкової видачі)

```
export/<ім'я клієнта>/<дата, напр. 17.08.26>/<матеріал-колір, напр. mono a3>/<файл>
```

- Проміжна папка — **дата скачування** (`дд.мм.рр`). Той самий день переюзує дата-папку, поки матеріал вільний; повтор матеріалу за день → `17.08.26 (2)`; новий день — нова папка. Старі `нова папка (N)` сумісні, глибина `клієнт/папка/матеріал` незмінна (`app/export_scanner.py`).
- Номер роботи в шляху не фігурує.
- **Два етапи руху файлів з пошти:** спершу все в спул `mail_attachments/<uid>/` (тріаж); при прийнятті — **move** у `export/...`. Відкат — назад у спул.
- Імена клієнтів у таблиці й папках різняться (одруківки, регістр) → нечітке зіставлення (`rapidfuzz`) + накопичувальний словник підтверджених пар.
- Зіставлення для видачі: клієнт + матеріал/колір + дата папки. Однозначно — авто; кілька — показати всі з часом, оператор обирає.

## 5. Статуси / життєвий цикл роботи

```
нове → прийнято → прораховано → у фрезеруванні → відфрезеровано
     → знайдено при видачі → видано
```

Окремі стани: проблема (коментар), переробка (n-й раз, причина + винуватець). **Брак впливає на гроші й звітність** — дані точні, з історією «хто що зробив»; CRM гроші не рахує, лише віддає цифри.

**Готовність — з двох полів**, не окремий статус (фільтр «Можна брати / В роботі / Не готово»):

| Стан | `job_code` | `sum3d_id` | Значення |
|---|---|---|---|
| Не готово | — | — | технік не здав |
| Можна брати | є | — | здав, не прораховано |
| В роботі | є | є | оператор взяв і прорахував |

## 6. Технічний стек (рішення вже прийняте)

Залежності — `requirements.txt`/`requirements-build.txt`. Нетривіальне:

- SQLite (не Postgres): ~**92 рядки/день** (лаба ~30, клієнти ~62; пік 130), максимум **двоє операторів**. Міграція на Postgres тривіальна через SQLAlchemy.
- Jinja2 + HTMX, без React/SPA — сервер рендерить фрагменти.
- Деплой: standalone Windows 10/11 x64, `127.0.0.1`, PyInstaller onedir + Inno Setup, автозапуск. Docker — додатково для dev.
- Окремий сервіс від CNC Tracker (різні цикли, ізоляція збоїв).

## 7. Вимога: секрети через інтерфейс, не тільки .env

Екран «Налаштування» (адмін): Google Sheet ID, service-account JSON, IMAP логін/пароль, шлях `export`. Зберігаються зашифровано в БД. У `.env` лише ключ шифрування. Безпечніше й зручніше (без ручного редагування файлів).

## 8. Дизайн-напрям (стартовий, буде уточнюватись)

Сучасний, анімований, технологічний, не типова admin-панель. Референс — Hex.tech:

- Темний майже чорний фон, тонка сітка-«блюпринт»
- Теплий кремово-рожевий (blush) акцент замість неонового кіберпанку — комфорт для очей цілий день
- Великий округлий жирний шрифт заголовків, дрібний акуратний текст
- Заокруглені картки з тонкою межею
- Чіп-теги зі знімним хрестиком (матеріал+колір у черзі)
- Моноширинний для ідентифікаторів — наряди, Sum3D ID, час
- Анімації стримані й функціональні, не декоративні

Дизайн-система — CSS custom properties в одному місці, легко доопрацьовувана (референси надходитимуть).

## 9. Екрани

0. Вхід — логін/пароль, акаунт на оператора (§10 `User`); без входу нічого не видно
1. Черга (основний, 90%) — незавершені роботи обох джерел, таби Сьогодні/Вчора/Завтра/Раніше; сортування за терміновістю, прострочені підсвічені; чіпи-фільтри; дії: взяти / копіювати шлях-ID для Sum3D (рівень 1 clipboard; рівень 2 `sum3d-open://` — на паузі) / скачати zip / статус
2. Нові з пошти (тріаж) — розпізнані поля на перевірку перед прийняттям
3. Картка роботи — паспорт, хронологія з іменем оператора, коментарі (двосторонні), файли, переробки
4. Видача — вчорашні й старіші невидані, шляхи з `export`, STL-прев'ю (головний інструмент звірки). Один крок: галочка «знайдено» знімає синю заливку рядка. Два вигляди одного списку — картки по клієнтах і рядки в порядку таблиці (`users.handout_flow`), порядок в обох однаковий. **Порядок стабільний** (§2). Кілька разів на день.
5. Статистика — одиниці/роботи по періодах, брак по причинах/винуватцях, час «нове → відфрезеровано»
6. Налаштування (адмін) — секрети (§7), оператори
7. Архів — поза робочим вікном; «Хроніка»: місяці → heatmap днів → роботи дня → паспорт read-only

## 14. Живі пастки й інваріанти

Історія фіч («що і чому зробили») — у `HISTORY.md`, не вантажиться автоматично; читати за потреби. Тут — лише те, що **досі кусає**. Одне джерело правди: не дублювати в памʼяті.

**Назва/реліз.** KuubMill (KMill). `GITHUB_REPO = "kuubek5/order-desk-releases"` не чіпати. Перший реліз після перейменування розірве авто-оновлення ОДИН раз (ассет `OrderDesk-Setup-…` → `KuubMill-Setup-…`) — інсталятор руками. Три міграції даних (тека `OrderDesk→KuubMill`, база `order_desk.db→kuubmill.db` з `-wal/-shm`, `ORDER_DESK_*`→`KUUBMILL_*`) не прибирати, поки не оновлені всі машини.

**Архітектура.** Бачить `Request`/будує `Response` → `app/routers/`; ні → `app/services/`. Роутери НЕ імпортують `web`. Два сторожі, знімки міняти лише свідомо: `tests/test_route_inventory.py` (множина метод+шлях) і `tests/test_frontend_assets.py` (JS-синтаксис, порядок скриптів, парсинг шаблонів, склад розділів налаштувань). CSS різано шматками, **порядок `<link>` у base.html і Є каскадом**. Після переносу коду `monkeypatch.setattr(web, "X")` мовчки стає no-op — тест зелений і порожній (один такий пустив IMAP-тест у справжню мережу); після переносу перевіряти, чи підміна влучає.

**Порожнє поле = «поля не було».** Кнопка вигляду, що шле порожнє значення, не вимикається: сервер читає `Form(None)` і для пропущеного поля, і для порожнього. Тому канонічний стан мусить мати ВЛАСНЕ слово (`clients`, `list` у `apply_handout_look`), яке в базі вже кладеться порожнім рядком. Двічі за один вечір: спершу порядок списку видачі, потім покажчик дня.

**Видача — один крок.** Галочка «знайдено» знімає синю заливку рядка, і це і є сигнал видачі. Кнопки «Видати» немає (07.09.26); роут `/handout/issue-group` лишили — уже видані роботи треба вміти повертати в чергу. Рядок роботи малюють ДВА режими списку через `_handout_work_row.html` — правити в одному місці.

**Теми.** Атрибут теми на `<html>`, не `body` (treatment-a будує похідні токени в `:root`). Нові кольори лише через `var()`, тема = один файл токенів.

**Черга.** Три канали рядка: **фон — стани** (6 заливок), **край — матеріал** (`inset box-shadow`, не `border-left`; цирконію смуги нема свідомо), **контур/шпилька — «мої зараз»** (`OrderFocus`, `?mine=1`; `focus` у роуті зайнятий підсвіткою). Новий сигнал шукає канал, а не 7-му заливку. `mine=1` мусить бути в `rows_qs`; `focused_ids` рахується в одному місці; усі рендери `_order_row.html` через `orders._row_context`. Полл кожні 15 с зберігає внутрішній скрол `.tablewrap`. Смуга печей і картка зміни стоять ВИЩЕ `.worklayout` (поза `#queue-rows`, який свапає полл) — усередині мигтіли б; згортання смуги — клас на `body` + localStorage.

**Retention/Архів.** Черга = 30 днів (`RETENTION_DAYS`), старше → Архів. Синк **нічого не видаляє назавжди** — зникла вкладка/рядок ставить `archived_at`. Фільтр черги і `order_is_archived` — точні доповнювачі, правити разом. Межа — від `business_today()`, ніколи `date.today()` (є тест-сторож, ловить і докстрінги).

**Зміна (/shift).** `open_notes()`/`open_note_count()` — один предикат (розійдуться → бейдж бреше). Поле написання поза `#shift-board` (свапається на `refresh-shift`). Час локальний, БЕЗ `server_default=func.now()` (на SQLite пише UTC — зсув 3 год). Три FK на `users` → `foreign_keys=[...]` на кожному relationship.

**Печі (VNC, лише читання).** Хибне число гірше за жодне: цифра або збігається з еталоном піксель-у-піксель, або поле порожнє; шаблон на весь рядок (`Zone.pattern`); смужка пікселів під числом — доказ, не прибирати. Великому шрифту температури бракує цифр 1,2,3,6,8 (`scripts/furnace_glyphs.py learn` на кадрі з ними). Статус — голосування ДВОХ сигналів (слово вгорі + кнопка внизу), і потрібні саме два згодні; третій («срок») лише звіряє й попереджає, призначити статус сам не може. Кадр раз на 6 с, рядок у БД — на зміну або раз на хв. Знімки паралельні, сесія БД на одному потоці. **`/settings/furnaces/password` оголошувати ВИЩЕ `/settings/furnaces/{furnace_id}`** (FastAPI зʼїдав «password» як id; є тест). Віджет показує лише печі З ДАНИМИ, екран — усі. Час відкриття київський. Порядок FTP > X-DREAM/OPC > VNC-OCR. `asyncvnc` тягне `TripleDES` зі старого місця `cryptography` — приберуть → впаде на підключенні.

**Пошта.** Watchdog `MAIL_SYNC_DEADLINE_SECONDS=180`; після timeout сесію не чіпати з іншого потоку (синк іде через `_run_mail_sync_owned_session`, зомбі лишають свідомо). Видалення архіву в `after_commit` + `after_rollback`, що роззброює хук. `rule.hits` — атомарний SQL. RAR потребує UnRAR/7z (шукається в типових теках, або `UNRAR_TOOL`). Скачування за посиланням — через legacy-renegotiation сесію (TLS-проксі лаби). Не можна прийняти лист із нескачаними файлами за посиланням — гейт на сервері. Водяний знак `since` у полі тріажу: правити `get_mail` і `_mail_triage_list.html` разом. `.btn.apex` — єдина залита кнопка на екран, лише прийняття листа. Не додавати анімацій-петель у тріаж.

**Матеріали vs винятки.** Синоніми матеріалів — `material_classifier.SEED_ALIASES` + міграція для наявних БД (seed-on-empty не долітає). Винятки «не наша робота» (3D-друк, моделювання) — ТІЛЬКИ через `MailFilterRule`/`MailFilterCategory`; паралельний `service_keywords` видалено як дубль, не відроджувати. Бейдж готовності — `triage_status.triage_readiness`.

**Шляхи.** `saved_path` вкладень — UNC (`\\host\share`), корені — з літерою (`P:\`); резолвер порівнює канонічні форми, інакше «Відкрити папку» 404. Помічники по шляхах у циклі рядків = сотні round-trip на мережеву шару — міряти виклики.

**Синк таблиці.** Читання вкладки — ОДИН `get_all_values`; `Cache-Control: no-cache`. Чанкове читання відкочено 01.09.26 (`410f8ad`), останній чанковий читач (`sheets.read_all_values`, лишався у знімках вкладок) прибрано 07.09.26 — діагноз «проксі обрізає велику відповідь» був хибний, роботи зникали через сірі СЛМ-рядки (фікс 0.6.5 — виключення за текстом «слм», не за кольором). Не відроджувати чанки. Знімки вкладок ходять під тим самим локом, що синк, і пропускають прохід при `quota_is_tight()`. Запобіжник масової архівації: >5 робіт І >25% за тік → пропуск. На гілці «вкладка зникла з листингу» — три запобіжники разом (08.09.26 один листинг без сьогоднішньої вкладки забрав в Архів робочий день): (1) довіра до листингу — найновіша вкладка ≥ вчора; вкладки наперед (09.09–14.09) її ОБМАНЮЮТЬ, тому сама по собі вона не захист; (2) вкладка робочого вікна (вчора/сьогодні/завтра) з >5 роботами → тримати й банер, незалежно від частки (день ≈ 10 % 30-денної черги, 25 % його не ловлять); (3) будь-яка інша вкладка мусить бути відсутня в 3 листингах ПОСПІЛЬ (`_absent_streak`, у памʼяті процесу, скидається щойно вкладка зʼявилась). Обходить лише `force_reconcile_tabs` — МНОЖИНА підтверджених вкладок, не булевий прапорець на весь прогін. Заархівований день повертається САМ: `sync_tab` бачить ту саму роботу в рядку і знімає `archived_at` через 10 хв після архівації. **Назва вкладки — лише через `canonical_tab_title()`** (`business_day`): 08.09.26 вкладка `" 08.09.26"` з пробілом на початку була для синку «недатованою», день стояв «Сьогодні 0» без жодного сліду (знімок вкладок мав власний `strip()` і її бачив). Новий парсер назв вкладок = та сама функція, не свій `strptime`. Сьогоднішньої вкладки нема серед датованих → запис у Журнал синку з листингом через `%r` — мовчазний пропуск дня заборонено. `SyncLog.occurred_at` — UTC (`server_default`); показувати ЛИШЕ через `utc_to_business` / фільтр `kyiv`, порівнювати з `utc_now()`, ніколи з `datetime.now()`. Таблиця головна для Sum3D: «можна брати» = `job_code` + порожній Sum3D, не fill-only. Пауза синку зупиняє читання й запис; синк сам не пише.

**Запис у таблицю.** Два незламні правила. (1) НЕ на event loop: роути `async def` пишуть лише через `await await_on_writeback(fn_warm, ...)` — воркер `sheet_writeback_pool` (один теплий потік, він же серіалізує записи), функції-`*_warm` беруть `order_id` і власну сесію, тож роут мусить закомітити ДО виклику. Роут, який пише синхронно, має бути звичайним `def` (threadpool), як `undo_action`. (2) Позиція рядка звіряється ЗАВЖДИ: `_resolve_row` / `resolve_order_row` / `clear_order_row`; `None` = пропустити запис (у т.ч. коли перевірочне читання впало — неперевірений рядок гірший за пропущений запис). Стирання (`clear_order_row`) без підтвердження не робиться ніколи: воно чистить A:K і знищило б чужу живу роботу.

**Копії Google-таблиці** (`app/sheet_backup.py`). Порожня вкладка не зберігається; свіжі 4 дні перезнімаються; різке падіння рядків (>5 і >25%) НЕ перезаписує копію (обрізане читання). Файли STL сюди не входять.

**Налаштування — меню, ролі й плити (06.09.26).** Меню, права на розділ і ключі — ОДИН реєстр `app/services/settings_nav.py`: рейка, гейти включень у `settings.html`, роути (`require_settings_edit`, `can_edit`), палітра Ctrl+K (`<script id="nav-data">`) і тести читають його. Розділ може бути ВКЛАДКОЮ іншого (`NavItem.parent`): партіал тоді має корінь `.stand-tabpane[data-tab=…]`, включається з господаря, а не з `settings.html`, і адреса `/settings#<ключ>` відкриває господаря одразу на цій вкладці. Так живуть «Копії таблиці» (в Google Таблиці), «Скачування вкладень» (у Пошті) і «Сповіщення» (у кабінеті /account). Новий розділ = рядок у `NAV` + партіал із таким самим `data-sec`/`data-tab` + плита в `build_slabs`; без когось із трьох упаде `tests/test_settings_nav.py` (там же знімок складу меню — міняти свідомо, як `route_inventory`). Оператор редагує «Джерела робіт» і «Обладнання» нарівні з адміном (рішення власника), АЛЕ write-проба шляху лишається адмінською — це запис у довільну мережеву шару, не налаштування. Плита розділу: колір ЛИШЕ з підтвердженого сигналу (heartbeat, кадр з пристрою, активний адмін); «поле заповнене» зеленим НЕ буває, шляхи не зеленіють ніколи. `slabs` — глобал `{}` у `deps.py`, бо партіали рендеряться і поза `/settings`. Тон-логіка — `tests/test_settings_status.py`, доїзд тону до HTML — `tests/test_settings_slabs_render.py` (справжній рендер через `tests/asgi_client.py`; httpx у venv немає, тому TestClient недоступний).

## 15. Робочий процес для Claude Code (з діагностики сесій, 17.08.26)

Правила з аналізу сесій (`SESSIONS_DIAGNOSTICS.md`) — економлять токени, прибирають повторні помилки. Дотримуватись у кожній сесії.

- **Порти:** `127.0.0.1:8000` — ПРОД (встановлений `KuubMill.exe`), `127.0.0.1:8002` — DEV. Не плутати; прод не чіпати без згоди.
- **Рестарт dev — одним кроком:** `.\dev_restart.ps1` (або `-Launch <шлях до dev_run.py>`). НЕ повторювати вручну «PID → Stop-Process → запуск → sleep → curl». WatchFiles не reload-ить `.py` — після правки Python рестарт обов'язковий.
- **Перевірка UI — спершу curl, не скриншот.** Логін через `POST /login` з cookie-jar. Скриншот — лише коли пейн видно.
- **Здача UI-фічі:** роут у curl — ще НЕ готово. (1) `node --check` на JS; (2) подія прив'язана (hx-атрибути / делегований listener); (3) видимий фідбек — «мовчазна кнопка» = не готово; (4) не можна перевірити клік з середовища → чесно «перевір ти».
- **Пошук — Grep-tool, не `grep` через Bash.** Кирилиця в консолі — мохібейк: вивід із кирилицею писати в UTF-8 файл у scratchpad і читати. Повторні python-перевірки — скриптом.
- **Секрети не в командному рядку.** Dev-ключ (`DB_ENCRYPTION_KEY`) — у gitignore-файлі, скрипт читає сам. Прод-ключ — DPAPI.
- **Реліз на прод:** скіл `kuubmill-release` (`.claude/skills/kuubmill-release/SKILL.md`), `/kuubmill-release`.
- **Закінчив блок (фіча закомічена) → новий чат.** Мегасесії стискають контекст, деталі губляться. `MEMORY.md` + коміти переносять усе.
- **Делегуй пошук/аналіз субагентам на дешевшій моделі.** «Де визначено X», масові grep, майнінг транскриптів — Haiku/Sonnet. Дорога модель — дивні баги (гонки, шифрування, міграції) і планування великих фіч.
- **Файл >150 рядків не читати цілком.** Grep за символом → Read з `offset/limit`. «Як працює X» → субагент Explore/Haiku: `file:line` + 3 речення, не текст. (Аудит 05.09.26: `sheets.py` 550 рядків заради 3 сигнатур.)
- **Перед скріншотом — `tabs_context`.** Пейн `hidden` → скрін/клік/скрол таймаутять по 30 с; тоді лише `read_page`/`get_page_text`/`javascript_tool`.
- **Паралельні чати — лише в окремих `git worktree`.** Два чати на одному дереві → гонка `route_inventory.txt`, фантомні падіння (05.09.26). `git worktree add ../CRM_Laba-<фіча>` перед другим чатом.
- **Дизайн-хук вимикати на рутинних правках** (`/impeccable hooks off`), один `/impeccable audit` наприкінці — спрацювання ≈ 500 токенів шаблону.
- **Змагальна перевірка перед здачею (08.09.26).** Правила вище перевіряють МЕХАНІКУ: чи відповів роут, чи валідний JS, чи прив'язана подія. Вони не питають, чи фіча правильна на реальних даних цеху — і три вади одного дня пройшли крізь усі них. Тому перед «готово» ще три питання:
  1. **Перший запуск на даних з історією, не в чистій кімнаті.** Сторож теки заготовок тестувався на порожній теці з трьома файлами, які я створив сам. У Роми там роки історії (номери до 891) — і перше ж натискання дало б комірниці замовлення на десятки тисяч дисків. Дані для перевірки мусять мати обсяг і минуле, а не збігатися з моєю моделлю світу.
  2. **Переходи, а не стани.** Дротель на покази верстата перевірявся тим, що він дротелить; момент ПАДІННЯ верстата тонув на 15 хв, бо перехід у відмову ніхто не пробував. Те саме з поверненням.
  3. **Перечитати власні коментарі проти коду.** Докстрінг обіцяв оптимізацію за часом теки, якої в коді не було. Жоден тест такого не ловить — лише читання написаного поруч із зробленим.
