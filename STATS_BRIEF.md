## 2. Що є в даних (розвідка 12.10.26)

**Можна рахувати вже зараз, на всій імпортованій історії:**
- роботи й одиниці по днях / матеріалах (`Order.material_id` — чистий каталог) / джерелах / клієнтах (`client_name` — вільний текст, нечіткий);
- обсяг по техніках (`Order.technician_name`, лише `source=="lab"`) — СКІЛЬКИ, але не ЯК ШВИДКО;
- час Sum3D — до секунди з самого ID (`HH-MM-SS`, `handout._SUM3D_TIME`, дата — з вкладки + межа 07:30);
- переходи статусів — `StatusEvent.occurred_at` (UTC): прийнято, прораховано, відфрезеровано, знайдено, видано;
- пошта: `EmailMessage.received_at` (київський, надійний з 25.09.26), прийняття ≈ `Order.created_at` роботи з `source_email_id`;
- фрезерування — лише 30 днів (`MachineReading`, межі за `sum3d_id`/`program_at`);
- брак — `ReworkRecord` (винуватець, одиниці переробки).

**НЕ записується (треба почати записувати — етап 0):**
- **момент, коли `job_code` вперше став непорожнім** — `sync.py:~1091-1112` робить простий `setattr`, події/часу немає. Без цього «наряд → відмодельовано» по техніках НЕ рахується взагалі, і заднім числом не відновлюється.
- **надійний час появи рядка**: `Order.created_at` = INSERT; для імпорту історії (`_INITIAL_LOOKBACK_DAYS`, «вся історія»), воскресіння з архіву й перевикористаного рядка (`_reset_order_for_new_work`) він хибний (усі рядки вкладки 30.06 мають 17.08 10:01).

## 3. Етап 0 — почати записувати (МАЛИЙ РЕЛІЗ, ПЕРШИМ)

Кожен день затримки = день історії, якої вже не буде.

- `Order.row_seen_at` (локальний київський, без `server_default` — `tests/test_timestamp_hygiene.py` стереже кількість UTC-дефолтів): ставить лише ЖИВИЙ тік синку, що створив роботу з рядка поточної вкладки. Імпорт історії, воскресіння, перевикористання рядка → NULL («невідомо»), а не хибний час.
- `Order.job_code_at` (локальний): ставить синк у гілці першого заповнення (`was_filled == False`), лише якщо робота існувала ДО цього тіку без шляху. Народилась зі шляхом → NULL (момент невідомий; у статистиці «наряд і шлях разом»). Шлях стерли й заповнили знову — час НЕ переписувати (рахуємо перше здавання).
- Точність ±15–25 с на «normal» (тік hot 15 с + читання ~3 с); на паузі синку / вимкненому ПК — момент наступного читання. Екран мусить казати «час техніків — з <дата релізу>».
- Тести: живий тік ставить `row_seen_at`; імпорт історії — ні; перше заповнення шляху ставить `job_code_at`; повторне — не чіпає; народжена зі шляхом — NULL. Прогін на копії бойової бази (DR: `scripts/dr_drill.py`).

## 4. Вкладки

Спільне: смуга періоду (30 днів за замовчуванням; 7 / 30 / 90 / свій діапазон), фільтри-чіпи (джерело лаба/пошта, матеріал, технік, клієнт), кожне велике число з «↑12 % до попередніх 30 днів». Клік по стовпчику/клітинці → бічна панель зі списком робіт (наряд, клієнт, матеріал, одиниці, час) і посиланням на паспорт. Експорт поточної вкладки в `.xlsx`.

1. **Огляд** — 4–6 чисел: одиниці за період, з них лаба/пошта, середньо на робочий день, медіана «наряд → модель» (з етапу 0), брак %, прогноз на цей тиждень з фактом. Під ними — одиниці по днях (стовпчики, лаба/пошта стосом).
2. **Надходження** — коли заходить робота: карта день тижня × година (одиниці), окремо лаба/пошта; частка поза робочими годинами; одиниці по матеріалах/кольорах у часі.
3. **Техніки** (лише адмін) — на техніка: одиниці, роботи, медіана й 80-й перцентиль «наряд → модель» (календарний час), частка «на швидку», брак з вини техніка. Сортування за будь-якою колонкою. Чесний підпис кількості вимірів (медіана з 3 робіт — не висновок).
4. **Пошта** — карта день×година за `received_at`; клієнти: одиниці за період, тренд (зростає / падає / зник — немає листів N днів при звичному ритмі); матеріали й кольори клієнтів пошти.
5. **Виробництво (затори)** — воронка медіан очікування по етапах: наряд → шлях → Sum3D → фрезерування → знайдено → видано; де робота чекає найдовше; розподіл (не лише середнє). Фрезерування — лише за 30 днів (телеметрія).
6. **Прогноз** — див. §6.

## 5. Робочі години

Налаштування (адмін): дні й години техніків (за замовчуванням Пн–Пт 9:00–18:00). Використовуються ЛИШЕ для «частки поза робочим часом» і тіні на карті день×година. Інтервали рахуються календарно (рішення власника).

## 6. Прогноз (тиждень наперед)

- **Що:** одиниці на кожен із 7 наступних днів — усього, лаба, пошта, по матеріалах (цирконій / ПММА / титан / інше).
- **День:** див. відкрите питання 2 (день вкладки чи календарний).
- **Модель — проста й перевірювана:** сезонна база за днем тижня (усічене середнє тих самих днів за 6–8 тижнів) × поправка тренду (останні 2 тижні до попередніх 6), окремо на кожне джерело/матеріал; діапазон (10–90-й перцентиль помилок минулого) поруч із числом. Жодного «чорного ящика».
- **Справність — чесно:** прогноз ЗАПИСУЄТЬСЯ в базу наперед (нова таблиця `ForecastSnapshot`: коли зроблено, на який день, серія, значення, діапазон, версія моделі) щодня о 07:30 (межа робочого дня). Факт порівнюється з ЗАПИСАНИМ, не перерахованим заднім числом. Показувати: прогноз vs факт по днях, середня помилка % за 30 днів, частка днів у межах ±15 %, і **порівняння з наївним прогнозом** («як тиждень тому») — модель корисна лише якщо його б'є.
- Мало історії (< 6 тижнів по серії) — показувати «замало даних», а не число.

## 7. Продуктивність і код

- Нинішній `stats.py` вантажить УСІ роботи з подіями в Python без фільтра дат — на рік це 25–35 тис. рядків. Нове — агрегати в SQL з фільтром періоду (індекси на дати), результат кешувати коротко; клік → список — окремий легкий запит.
- Дні: `business_today()` / `tab_day`, ніколи `date.today()`; UTC-поля — через `utc_to_business`.
- Розмітка — сервер (Jinja + HTMX), вкладки — фрагменти; графіки — inline SVG без бібліотек, кольори лише з токенів (`var()`), тема = токени. Перед графіками — скіл `dataviz`.
- Телефон: вкладки прокручуються, карти й таблиці — в одну колонку, клік → список на всю ширину.
- Сторожі: `test_route_inventory`, `test_frontend_assets`, `test_settings_nav` (якщо з'являться налаштування годин).

## 9. Вирішено власником (друге коло, 12.10.26)

1. **Імена техніків — зводити автоматично регістр і латиницю↔кирилицю** («с»/«c»/«С» → один, «Даня»/«ДАня» → один, «Gеніс» → «Геніс»). Без словника й підтверджень. Різне НАПИСАННЯ (Kira / кіра) лишається окремо. Зведення — одна функція (ключ групування), показувати найчастіше написання групи.
2. **Дні — як у таблиці** (день вкладки; п'ятниця = пт+сб+нд, `business_day.tab_day`), і для графіків, і для прогнозу.
3. **Дні-аномалії позначає адмін** (клік по дню → «нетиповий»); прогноз на них не вчиться, а в журналі точності вони видні окремо.
4. **Етап 0 — новий чат, першим**, окремим малим релізом.
