# Меню налаштувань — структура й ролі (06.09.26)

Мокап: `screens/settings_nav_variants.html` (перемикач варіантів + перемикач ролі).
Рамки: **жодна кнопка не зникає** — 20 пунктів меню + 2 сироти (`/diag/perf`, `/license`),
усі 60+ роутів лишаються. Змінюється лише те, як їх знаходять.

## 0. Що зараз і чому воно ламке

Меню живе в `_topbar_nav.html` (рядки 34–185): 6 груп, 20 посилань, **7 окремих
`{% if user.role == 'адмін' %}`**. Ще один гейт — у `settings.html` (навколо групи include'ів),
ще по одному — в кожному роуті. Три місця, які мають збігатися руками.
Палітра `Ctrl+K` зчитує DOM рейки (`settings_console.js:70`) — тобто наслідує ці ж гейти,
але лише те, що вже відрендерено.

Симптоми:

## 1. Архітектура (спільна для всіх варіантів)

Одне джерело правди — **реєстр у Python**, а не в шаблоні:

```python
# app/services/settings_nav.py
@dataclass(frozen=True)
class NavItem:
    key: str            # = data-sec секції або slug сторінки
    title: str
    href: str           # "/settings#sheets" | "/settings/materials" | "/journal/sync"
    kind: str           # "section" (swap на /settings) | "page" (окрема сторінка)
    roles: frozenset[str] | None   # None = усі ролі; адмін бачить усе завжди
    icon: str
    keywords: tuple[str, ...] = ()  # для Ctrl+K: "export", "пошта", "оновлення"
    badge: str | None = None        # ключ живого бейджа (sync_dot, pending_mail…)

@dataclass(frozen=True)
class NavGroup:
    key: str
    title: str
    items: tuple[NavItem, ...]

NAV: tuple[NavGroup, ...] = (...)          # ← єдине місце, де описано меню

def visible_nav(user, db) -> list[NavGroup]:

    Порожні групи випадають — оператор не бачить заголовків без пунктів."""

```

Хто споживає реєстр:

| Споживач | Зараз | Стане |
|---|---|---|
| Рейка `_topbar_nav.html` | 150 рядків розмітки з 7 гейтами | один `{% for group in nav %}` |
| Гейт include'ів у `settings.html` | `{% if user.role == 'адмін' %}` навколо 6 партіалів | `{% if can_see('sheets') %}` на кожному |
| Роути (`403`) | `if user.role != "адмін"` у кожному | `require_nav(key)` — та сама таблиця |
| Палітра `Ctrl+K` | скрейп DOM | `<script type="application/json" id="nav-data">` з того ж `visible_nav` + `keywords` |
| Плити стану (`build_slabs`) | окремий словник ключів | ключі беруться з реєстру — новий розділ без плити не пройде тест |
| Блокування розділів (`section_gate.SECTIONS`) | свій міні-реєстр | стає полем `gate: bool` у `NavItem` |

**Ролі.** `roles` — множина, не булеве. Адмін бачить усе завжди (як у `section_gate`).
Нова роль зʼявляється в акаунтах — і одразу працює: пункти з `roles=None` вона бачить,
адмінські — ні, точкові — за переліком. «Блокування розділів» уже вміє таргетити ролі
з БД (`non_admin_roles`) — той самий механізм.

**Два види пунктів мають виглядати по-різному.** `kind="page"` отримує маленьку стрілку ↗
праворуч — оператор розуміє, що сторінка перезавантажиться, а не перемкнеться на місці.

**Тести, які роблять «кожна кнопочка працює» перевірюваним, а не обіцянкою:**

1. `test_nav_every_item_resolves` — кожен `href` реєстру є в `route_inventory.txt`
   (для `#hash` — існує секція з таким `data-sec` у `_settings_*.html`).
2. `test_nav_every_section_is_registered` — кожен `data-sec` у партіалах є в реєстрі
   (сирота в DOM = недосяжна з меню = баг).
3. `test_nav_roles_match_routes` — для кожної ролі: `GET` кожного видимого пункту → `200`,
   кожного невидимого → `403`/редирект. Ловить розсинхрон «меню показує, роут забороняє».
4. `test_nav_no_empty_groups_for_operator` — оператор не бачить заголовків без пунктів.
5. Знімок `test_frontend_assets` тримає **склад реєстру**, а не розмітку рейки.

## 2. Три варіанти структури

Спільні переміщення в усіх трьох (виправляють симптоми 2, 3, 6):
«Копії Google-таблиці» → поруч із «Google Таблиця»; «Зворотний звʼязок» → до системи;
«Швидкодія» (`/diag/perf`) і «Ліцензія» (`/license`) → у меню, лише адмін.

### V1 · «За потоком цеху»

Групи в порядку, в якому робота йде цехом — той самий порядок, що в головній рейці
(Черга → Пошта → Видача → Печі → Верстати). Адмін бачить 5 груп, оператор — 3.

| Група | Пункти | Роль |
|---|---|---|
| Огляд | Стан системи · Журнал синку · Журнал дій | всі / адмін / всі |
| Джерела робіт | Google Таблиця · Копії таблиці · Пошта (IMAP) · Скачування вкладень · Фільтри пошти · Матеріали | адмін |
| Цех | Шляхи папок · Пічки · Верстати | всі / адмін / адмін |
| Люди й доступ | Оператори · Блокування розділів · Мій акаунт | адмін / адмін / всі |
| Система | Сповіщення · Резервна копія · Зворотний звʼязок · Швидкодія · Ліцензія · Про застосунок | всі / адмін / адмін / адмін / адмін / всі |

*За:* найменша зміна звички — групи впізнавані, порядок = порядок цеху.
*Проти:* ролі всередині груп перемішані; оператор бачить «Цех» з одним пунктом.

### V2 · «Моє / Адміністрування» (рекомендую)

Спершу поділ за **ким**, потім за **чим**. Класика SaaS (Personal ↔ Workspace):
усе, що стосується цього робочого місця й цієї людини, — одна група нагорі, для всіх;
усе адмінське — нижче, під власним заголовком. Оператор бачить **рівно одну групу**
без жодного порожнього заголовка. Адмін бачить 1 + 4.

| Група | Пункти | Роль |
|---|---|---|
| **Моє робоче місце** | Мій акаунт · Сповіщення · Шляхи папок · Журнал дій · Про застосунок | всі |
| Джерела робіт | Google Таблиця · Копії таблиці · Пошта (IMAP) · Скачування вкладень · Фільтри пошти · Матеріали | адмін |
| Обладнання | Пічки · Верстати | адмін |
| Люди й доступ | Оператори · Блокування розділів | адмін |
| Обслуговування | Стан системи · Журнал синку · Резервна копія · Зворотний звʼязок · Швидкодія · Ліцензія | адмін |

*За:* ролі — це структура, а не фільтр: третя роль (логіст) додається як група або як
`roles` на пункт, і меню не розсипається. Для оператора найкоротше меню з усіх варіантів.
*Проти:* «Стан системи» ховається в «Обслуговування» — оператор його не бачить. Якщо він
має бачити стан — пункт лишається у «Моє робоче місце» (кнопки перевірки й так адмінські).

### V3 · «Хаб + вкладки» (на виріст)

Рейка тримає **5 пунктів**, а не 20. Кожен — власна сторінка з горизонтальними вкладками
всередині (`/settings/sources`, `/settings/shop`, …). Пошук по вкладках — `Ctrl+K`.

| Рейка | Вкладки |
|---|---|
| Огляд | Стан · Журнал синку · Журнал дій · Швидкодія |
| Джерела | Таблиця · Копії · Пошта · Скачування · Фільтри · Матеріали |
| Цех | Шляхи · Пічки · Верстати |
| Люди | Оператори · Блокування · Мій акаунт |
| Система | Сповіщення · Бекап · Зворотний звʼязок · Ліцензія · Про застосунок |

*За:* масштабується до 40 розділів без довгої рейки; URL = `/settings/sources#imap` — читабельний.
*Проти:* найдорожче: `settings.html` розпадається на 5 сторінок, `settings_console.js`
переписується, знімок `route_inventory` міняється на 5 нових роутів. Робити після реєстру, не замість.

## 3. Рекомендація

**Реєстр (§1) — у будь-якому випадку**, це і є «архітектурно акуратно»: один файл описує меню,
ролі й ключі розділів, а рейка, гейти, палітра й тести читають його. Без нього будь-яке з трьох
групувань — це знову правка розмітки в семи місцях.

Групування — **V2**. Причина одна: ролі в ньому — структура, і питання «а що бачить логіст»
відповідається одним рядком у реєстрі, а не новим `{% if %}`.
V3 — коли розділів стане понад 25.

## 4. Порядок робіт (якщо погоджено)

1. `settings_nav.py` + тести 1–5 — на **поточному** групуванні, нічого не рухаючи. Зелено = нічого не загубили.
2. `_topbar_nav.html` → цикл по реєстру; `settings.html` → `can_see`. Знімки сторожів оновити свідомо.
3. Перегрупувати за V2 — це вже лише зміна порядку в одному tuple.
4. Сироти в меню: «Швидкодія», «Ліцензія».
5. Стрілка ↗ на `kind="page"`.
