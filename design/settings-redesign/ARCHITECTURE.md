# Налаштування — архітектура редизайну (06.09.26)

Мокапи: `screens/settings_v2_variants.html` (вкладки: Діагноз · A · B · C).
Джерела: живий `/settings` на 8002 (тема **forge**), інвентар 14 партіалів, `design/audit_2026-09-05/ux_settings.md`.

## 0. Що лишається недоторканим

Редизайн **не чіпає** роути, форми, HTMX-обв'язку, гейти ролей і те, що вже добре:

- ліва рейка з групами й прогресом `5/5` (`_topbar_nav.html`) — найсильніша частина екрана;
- «одна секція на екран» через `settings_console.js` (`.is-shown`), `#hash`, палітра `Ctrl+K`;
- 14 партіалів як одиниці рендеру; ~50 роутів; сторожі `test_route_inventory.py` / `test_frontend_assets.py`.

Змінюється **тільки макет усередині секції** + один новий рівень поверхні в токенах.

## 1. Діагноз (8 поломок)

| # | Поломка | Наслідок |
|---|---|---|
| 1 | Секція = один стовп на всю ширину | контент у верхніх 55%, нижче пустка |
| 2 | Проза-інструкції всередині форми | тексту більше, ніж контролів |
| 3 | Поверхні різняться на 3–5% яскравості | не видно межі «картка / поле вводу» |
| 4 | Стан — сірий чіп 11px у кутку | головна відповідь адміну захована |
| 5 | Дії без сталого місця | «Зберегти» щоразу в іншому кутку |
| 6 | Один контейнер на 2 поля і на таблицю з 9 колонок | одна секція порожня, друга тісна |
| 7 | Руйнівна дія виглядає як проба | «Встановити vX» = «Перевірити доступ» |
| 8 | Заголовок «Налаштування» на всіх 14 розділах | контент не підхоплює орієнтир рейки |

## 2. Чотири сутності (спільний кістяк усіх варіантів)

**Розділ** — назва · призначення одним рядком · **стан** · основна дія.
Обирає одну з трьох форм: `форма` (Google, IMAP, Шляхи), `реєстр` (Пічки, Верстати, Оператори, Фільтри), `довідка` (Про застосунок, Стан системи).

**Група** — смисловий блок полів («Підключення», «Поведінка синку», «Разові дії»), із заголовком, згортається.

**Поле** — підпис + контрол + підказка + слот живої перевірки (той самий, куди зараз б'є HTMX `check-path`). Три ширини: ⅓ / ½ / повна. **Ніколи не «завжди на всю»**.

**Дія** — три класи з фіксованим місцем:
- *основна* — панель збереження (з'являється на `dirty`), залита акцентом;
- *проба* — read-only, завжди контурна, живе поруч зі станом;
- *руйнівна* — червона, у блоці **«Небезпечна зона»** внизу розділу, завжди з підтвердженням.

«Небезпечна зона» закриває пункт аудиту: 7 руйнівних дій без бар'єра (оновлення, скидання пароля, спільний VNC-пароль, імпорт історії, відключення OAuth, відновлення з бекапу, toggle-active).

## 3. Токени: один новий рівень

Додається рівно одна змінна — поверхня вводу, **нижча** за картку:

```css
--well: #100c06;   /* forge; свій відтінок на кожну тему */
```

Шкала фіксується: `rail < page < card < well`. Поле вводу завжди «втоплене», а не «наліплене». Решта кольорів — наявні токени, нових немає (CLAUDE.md §14 «Теми»).

## 4. Три варіанти

### A · «Панель» — двоколонковий каркас
Ліворуч контроли (макс ~720px) у картках-групах, праворуч липкий стовпчик **Стан / Перевірки / Як це працює**. Панель збереження липне до низу. Пристрої — компактна таблиця з inline-полями.

*За:* лікує всі 8 поломок мінімальною зміною; проза йде вправо й заповнює пустку; найдешевше в реалізації (перекладання наявних партіалів у 2-колонковий грид).
*Проти:* найконсервативніше; на вузькому вікні бічна колонка падає вниз.
*Ціна:* низька — CSS + перестановка блоків, HTMX не чіпається.

### B · «Стенд» — статус-плита першою
Кожен розділ починається плитою на всю ширину: 4 живі метрики + основна дія (як приладова панель цеху). Нижче — сітка комірок 6 колонок (поле займає 2/3/4/6). Обладнання — **картки-пристрої** з портретом, станом і тегами замість таблиці.

*За:* найкраще відповідає продукту (перегукується з екранами Печей і Верстатів, з арт-напрямом «жар коронок»); стан неможливо не побачити; порожнеча зникає структурно.
*Проти:* метрики треба реально порахувати на сервері (частина вже є: heartbeat, self-check, вага таблиці); картки-пристрої займають більше висоти, ніж таблиця, при 10+ верстатах.
*Ціна:* середня — новий компонент «плита» + «картка пристрою», нові дані в контекст.

### C · «Верстак» — master-detail з інспектором
Три колонки: рейка → список параметрів/сутностей розділу → інспектор праворуч. Простий розділ (IMAP) стає списком параметрів; складний (Верстати) — списком пристроїв. В інспекторі: значення + стан + **історія змін параметра** («11.08.26 · Рома замінив JSON-ключ»).

*За:* масштабується без болю (буде 25 розділів — макет не зламається); природно вміщує `ActionLog` і журнал синку; пошук `Ctrl+K` стає повноцінним — шукає **параметри**, не лише розділи.
*Проти:* найдорожче; ламає «одна секція = один партіал» (треба розбити партіали на параметри); на вузькому вікні три колонки не живуть.
*Ціна:* висока — новий рівень моделі («параметр» як сутність з історією).

## 5. Рекомендація

**A як база + дві речі з B.** A дає весь виграш за найменші гроші й не чіпає HTMX; з B беремо статус-плиту для розділів, де стан — головне (Google, IMAP, Верстати, Пічки, Стан системи) і картки-пристрої для обладнання. C тримати як напрям на потім: його інспектор із історією стане природним, коли `ActionLog` доросте до налаштувань.

Порядок робіт: `--well` і класи-атоми → «Небезпечна зона» (закриває аудит) → сітка полів у Google/IMAP/Шляхи → бічна колонка стану → реєстри обладнання → панель збереження на `dirty`.

## 6. Що перевірити перед реалізацією

- порядок `<link>` у `base.html` — CSS каскадом (CLAUDE.md §14);
- `tests/test_frontend_assets.py` тримає **склад розділів налаштувань** — знімок міняти свідомо;
- `/settings/furnaces/password` вище `/settings/furnaces/{id}` — не переставляти;
- `--well` завести в кожну тему (`tokens.css`, `theme-forge.css`, `treatment-a.css`), не хардкодити.
