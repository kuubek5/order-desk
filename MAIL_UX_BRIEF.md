## Головне правило

Наявний функціонал пошти **працює добре — не ламати**. Обидві фічі **additive**:
нове поле + новий вибір, стара логіка приймання/папок/запису недоторкана. Сторожі
`route_inventory`, `frontend_assets`, `settings_nav` мусять лишитись зелені (нові
роути = свідома зміна знімка).

## Дві задачі

### 1. Ім'я відправника в списку тріажу (як ukr.net)

**Біль.** Оператор звик обробляти пошту за показним іменем відправника
(«Юрій Струбицький», «Євген Кривовид») — так виглядає ukr.net. У нас список
показує `client_name_guess or from_address`: коли класифікатор не вгадав клієнта,
видно голу адресу, не людину.

**Причина в коді.** При імпорті беремо лише `from_address=msg.from_`
([mail_reader.py:686](app/mail_reader.py:686)) — це сама адреса. imap-tools дає
показне ім'я окремо (`msg.from_values.name`), але ми його **викидаємо**.

**Рішення (рішення власника: ім'я відправника головним, здогад — підказкою).**
1. Нове поле `EmailMessage.from_name` (`String(200)`, nullable) —
   [models.py:590](app/models.py:590) поруч із `from_address`. Міграція (seed на
   існуючих: лишити NULL, беккфіл не обов'язковий — нові листи заповняться самі;
   якщо легко — розпарсити з наявного, але не критично).
2. У читачі писати `from_name=<показне ім'я>`
   ([mail_reader.py:682](app/mail_reader.py:686)). Джерело — `msg.from_values`
   (imap-tools `Address.name`). Перевірити, що поле реально приходить; fallback —
   `email.utils.parseaddr(msg.from_)[0]`.
3. У списку ([\_mail_triage_list.html:50](app/templates/_mail_triage_list.html:50))
   головним рядком показувати `from_name or client_name_guess or from_address`.
   Здогад класифікатора — другим рядком/підказкою (він потрібен для теки й
   приймання, тож нікуди не дівається; лише перестає бути головним написом).
4. НЕ чіпати `client_name_guess`, візард, приймання, sender-memory — воно все
   лишається на здогаді.

**Перевірка:** справжній лист у фантомну скриньку (§12), відкрити тріаж на dev,
переконатись що показне ім'я збіглося з ukr.net; лист без показного імені падає
на здогад/адресу.

### 2. Груповий Sum3D ID у черзі (один ID → N робіт)

**Біль.** Sum3D ID оператор має **ПІСЛЯ прийняття** (прийняв листи → порахував у
Sum3D → отримав time-id). Зараз вписує **вручну на кожну роботу** в черзі. Один
Sum3D-проєкт часто накриває **кілька клієнтів з пошти** (і навіть лаба+пошта в
одному проєкті) → той самий id доводиться вписувати N разів.

**Рішення (рішення власника: варіант А — мультивибір у ЧЕРЗІ).** Черга покриває
будь-яке джерело (лаба+пошта), і безпечний запис Sum3D уже живе тут.

**Цегла, яку переюзати — НЕ винаходити.** Одиночний потік:
`POST /orders/{order_id}/sum3d-id` ([orders.py:141](app/routers/orders.py:141),
`async def set_sum3d_id`). Він робить рівно те, що треба на кожну роботу:
- `order.sum3d_id = value`;
- вписаний Sum3D = момент «прорахував» → авто-статус/стемп листа;
- чистить `order.sum3d_pending`;
- кладе запис у пул `sheet_writeback_pool` через `*_warm` (НЕ на event loop);
- лог `ActionLog(action_type="sum3d")` для undo.

**План:** винести спільне ядро одиночного роуту у функцію
`apply_sum3d(db, order, value, operator)` (усе вище, крім HTTP/тоста/рендеру).
Одиночний роут кличе її на одну роботу; новий батч-роут — у циклі по вибраних.
Кожна робота йде через `_resolve_row`/`resolve_order_row` (§14 «Запис у таблицю»):
позиція рядка звіряється щоразу, `None` = пропустити цей рядок, решту записати —
чесний тост «записано K з N, пропущено M».

**UI в черзі — з оглядкою на § «Черга» (інваріанти святі):**
- Чекбокси на рядках стану «можна брати»/«не готово» (роботи без Sum3D).
- Вибрав ≥1 → спливає смуга дії: `Sum3D ID [_______]` + «Призначити N».
- Один POST `/orders/sum3d-batch` (`order_ids[]` + `sum3d_id`) → `apply_sum3d` в
  циклі → один комміт до виклику warm-функцій (роут `async` пише лише через
  `await await_on_writeback`, або зробити роут звичайним `def` у threadpool як
  `undo_action` — обрати за патерном сусідів).
- **Порядок списку стабільний** — вибір не пересортовує. Полл кожні 15с
  (`#queue-rows` swap) НЕ повинен губити вибір: або client-side стан
  переставляється після swap (як `.active`/unread у пошті через app.js), або
  вибрані рядки поза зоною свапу. Смуга дії — як смуга печей, ВИЩЕ `#queue-rows`,
  інакше мигтітиме.
- Рендер рядків лишається через `orders._row_context` + `_order_row.html` (обидва
  режими). Чекбокс додати в один шаблон рядка.
- `route_inventory` знімок оновити свідомо (новий POST).

**Перевірка (§15, змагальна):** на dev + тестова Google Таблиця (§12) — вибрати
3 роботи, призначити один id, **подивитись у самій таблиці**, що id ліг у всі три
правильні рядки (не в чужі), статус зрушив, undo працює на кожній. Перевірити
випадок, коли `_resolve_row` вертає `None` (зсунений рядок) — запис пропущено, не
затерто чуже, тост чесний.
